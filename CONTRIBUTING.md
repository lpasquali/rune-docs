# Contributing to RUNE

Thanks for considering a contribution. This file is the ecosystem-wide entry point — it covers **any** RUNE repository (`rune`, `rune-operator`, `rune-ui`, `rune-charts`, `rune-docs`, `rune-audit`, `rune-airgapped`, `rune-ci`). Repository-specific details live in each repo's README and in [docs/usage/DEVELOPER_GUIDE.md](docs/usage/DEVELOPER_GUIDE.md).

All the authoritative process rules live in [docs/context/SYSTEM_PROMPT.md](docs/context/SYSTEM_PROMPT.md). This page is a human-friendly pointer, not a restatement.

## Before you open an issue

- **Labels**: see [docs/delivery/LABELS.md](docs/delivery/LABELS.md) for the canonical label set (`type/*`, `priority/*`, `area/*`, `swimlane:*`, agent-lane `*_cli`).
- **Take-issue protocol**: when you (human or agent) want to own an issue, follow [SYSTEM_PROMPT §Take issue (user-directed)](docs/context/SYSTEM_PROMPT.md#take-issue-user-directed). Assign to `lpasquali` (never self-assign), apply your agent-lane label (`claude_cli` / `gemini_cli` / `copilot_cli` / `cursor_cli`), remove other agent-lane labels, isolate on a feature branch, then set Project #1 Status → **In progress**.
- **Agent-lane labels** (`*_cli`) exist so the Project #1 **Agent Lane** field is unambiguous. Only one agent-lane label per item.

## Before you open a PR

- Copy the repo's `.github/PULL_REQUEST_TEMPLATE.md` verbatim. The layout is shared across all eight repos.
- Pick exactly **one** DoD level and tick its box:
  - **Level 1 — Full Validation** (runtime, API, Helm, Dockerfile): docker-compose E2E + kind E2E + standalone CLI E2E + breaking-change review + dependency CVE audit. See [docs/usage/E2E_TESTING.md](docs/usage/E2E_TESTING.md) for the binding E2E contract (landing under PR [#272](https://github.com/lpasquali/rune-docs/pull/272)).
  - **Level 2 — Test Infrastructure** (test config, CI, coverage, linter): full test suite + coverage not degraded + no CI regressions.
  - **Level 3 — Documentation** (Markdown, MkDocs, diagrams in rune-docs): `mkdocs build --strict` + `pymarkdown scan README.md docs` + peer review.
- **Acceptance Criteria Evidence**: every ticked criterion needs proof (CI logs count, screenshots for UI changes, command output for CLI changes).
- **Audit Checks**: report `PASS` / `FAIL` / `No triggers fired` per row. If any row is `FAIL`, the PR should not merge. See [docs/delivery/AUDIT_AGENTS.md](docs/delivery/AUDIT_AGENTS.md) for when each check triggers.
- **Breaking Changes**: must be declared, even if "None".
- CI enforces all of the above via the `RuneGate/Process/PR-Body-Compliance` check. Failing the check blocks merge.

## Development setup

Per-repo environment setup, build/test/lint commands, and DoD validation steps live in [docs/usage/DEVELOPER_GUIDE.md](docs/usage/DEVELOPER_GUIDE.md).

If you are starting from a fresh machine, see [docs/operations/WORKSTATION.md](docs/operations/WORKSTATION.md) for Ubuntu 24.04 tooling installation (Python 3.14, Go 1.25, Docker, `kind`, `kubectl`, `helm`, scanners).

## E2E testing

Level-1 PRs must attach an `e2e-artifacts/summary.md` generated by `scripts/e2e.sh` per the contract in [docs/usage/E2E_TESTING.md](docs/usage/E2E_TESTING.md) (binding spec lands via PR [#272](https://github.com/lpasquali/rune-docs/pull/272); per-repo wrapper scripts land in Phase 1 under the same epic).

## Security disclosure

Please do **not** open public issues for security vulnerabilities. Use the disclosure process in [SECURITY.md](SECURITY.md) at the repo root.

## Questions and discussions

- **General questions**: open a GitHub Discussion in the relevant repo.
- **Feature requests**: open an Issue with `type/enhancement` + the appropriate `area/*` label.
- **Cross-repo architectural questions**: an ADR in `rune-docs/docs/architecture/adrs/` — see existing ADRs for format. ADR id + title must land in `docs/context/CURRENT_STATE.md`.

## Code of conduct

By participating in any RUNE repository, you agree to abide by the Code of Conduct in `CODE_OF_CONDUCT.md` where present. Be patient, be kind, be honest about uncertainty.
